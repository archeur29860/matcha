Blueprint `interaction_bp`, préfixe `/api/interaction`. Code : `back-matcha/routes/interaction_bp.py` et `back-matcha/services/interaction_service.py`.

Chaque action d'un utilisateur sur un autre est historisée dans la table `interactions`. Types acceptés (enum `type_of_interaction`) : `Liked`, `Unliked`, `Viewed`, `Blocked`, `Reported`.

## Créer une interaction

`POST /api/interaction/`

<ParamField body="from_user_id" type="string (UUID)" required>
  Auteur de l'interaction.
</ParamField>

<ParamField body="to_user_id" type="string (UUID)" required>
  Cible. Doit être différente de `from_user_id`.
</ParamField>

<ParamField body="which_interaction" type="string" required>
  `Liked`, `Unliked`, `Viewed`, `Blocked` ou `Reported`.
</ParamField>

```bash
curl -X POST http://localhost:5000/api/interaction/ \
  -H "Content-Type: application/json" \
  -d '{"from_user_id": "<uuid>", "to_user_id": "<uuid>", "which_interaction": "Liked"}'
```

Réponse `201` :

```json
{
  "success": true,
  "data": {
    "interaction": {
      "id": "<uuid>",
      "from_user_id": "<uuid>",
      "to_user_id": "<uuid>",
      "which_interaction": "Liked",
      "created_at": "..."
    },
    "match": null,
    "match_created": false,
    "match_deleted": false
  },
  "error": null
}
```

<Note>
  La création et la suppression automatiques de match sont commentées dans le code : `match`, `match_created` et `match_deleted` valent toujours `null` / `false` pour le moment.
</Note>

| HTTP | Code | Cause |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | Champ manquant, UUID invalide, identifiants identiques ou type inconnu |
| 404 | `FROM_USER_NOT_FOUND` | `from_user_id` n'existe pas |
| 404 | `TO_USER_NOT_FOUND` | `to_user_id` n'existe pas |
| 409 | `INTEGRITY_ERROR` | Autre violation de contrainte |

## Interactions émises

`GET /api/interaction/from/{user_id}/`

Interactions faites par `user_id`, de la plus récente à la plus ancienne. `user_id` dans chaque élément désigne la cible.

<ParamField path="user_id" type="string (UUID)" required>
</ParamField>

<ParamField query="limit" default="20" type="integer">
</ParamField>

<ParamField query="cursor" type="string">
</ParamField>

```bash
curl "http://localhost:5000/api/interaction/from/<uuid>/?limit=20"
```

```json
{
  "success": true,
  "data": {
    "items": [
      {
        "id": "<uuid>",
        "username": "mlefevre_12",
        "user_id": "<uuid>",
        "which_interaction": "Viewed",
        "created_at": "..."
      }
    ],
    "pagination": {
      "next_cursor": { "created_at": "...", "id": "<uuid>" },
      "has_more": true
    }
  },
  "error": null
}
```

<Warning>
  `next_cursor` est un objet, alors que la route transmet le paramètre `cursor` au service sous forme de chaîne. La pagination au-delà de la première page n'est donc pas encore fonctionnelle.
</Warning>

## Interactions reçues

`GET /api/interaction/to/{user_id}/`

Interactions dont `user_id` est la cible. `user_id` dans chaque élément désigne l'auteur. Mêmes paramètres et format que ci-dessus, plus :

<ParamField query="typeof_inter" type="string">
  Filtre sur un type d'interaction (par exemple `Liked` pour savoir qui a liké le profil).
</ParamField>

```bash
curl "http://localhost:5000/api/interaction/to/<uuid>/?typeof_inter=Liked"
```

## Vérifier un like

`GET /api/interaction/{from_user_id}/{to_user_id}/`

Vérifie si la dernière interaction `Liked`, `Unliked`, `Blocked` ou `Reported` de `from_user_id` vers `to_user_id` est un `Liked`.

```bash
curl http://localhost:5000/api/interaction/<uuid>/<uuid>/
```

<Warning>
  La route renvoie actuellement `success(isLiked)` (la fonction elle-même) au lieu de la variable `isliked`. La réponse ne contient donc pas le booléen attendu tant que ce bug n'est pas corrigé.
</Warning>
