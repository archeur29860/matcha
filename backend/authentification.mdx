L'authentification repose sur trois éléments :

1. le blueprint `auth_bp` (`routes/authenticate_bp.py`), qui expose [`POST /api/auth/`](/api/authentification) ;
2. le service `authenticate_service`, qui récupère l'utilisateur en base ;
3. Flask-JWT-Extended, qui génère et vérifie les tokens.

## Hachage des mots de passe

Les mots de passe ne sont jamais stockés en clair. `services/users_service.py` les hache avec `werkzeug.security.generate_password_hash` à la création et à la modification d'un utilisateur (voir [Utilisateurs](/api/users)). Le [seed](/backend/seed) utilise la même fonction.

## Connexion

`POST /api/auth/` vérifie dans l'ordre :

1. la présence d'un corps JSON ;
2. la présence de `email` et `password` ;
3. l'existence de l'utilisateur (`get_authenticate_user`) ;
4. la correspondance du mot de passe avec `check_password_hash`.

Toute erreur lève une `ValidationError` (`400 VALIDATION_ERROR`). En cas de succès, la route renvoie un token et les informations de base de l'utilisateur.

## Génération du token

```python
from flask_jwt_extended import create_access_token

access_token = create_access_token(identity=str(user["id"]))
```

L'identité du token est l'UUID de l'utilisateur. La clé de signature est lue dans `app.py` :

```python
JWT_SECRET_KEY = os.environ["JWT_SECRET_KEY"]
app.config["JWT_SECRET_KEY"] = JWT_SECRET_KEY
jwt = JWTManager(app)
```

<Warning>
  `JWT_SECRET_KEY` doit être définie dans le `.env` (voir [Installation](/installation)). Toute personne qui la connaît peut forger des tokens valides.
</Warning>

## Protéger une route

Ajoutez `@jwt_required()` et récupérez l'identité avec `get_jwt_identity()`, comme dans [`/api/connected/`](/api/connected) :

```python
@connected_bp.route("/", methods=["GET"])
@jwt_required()
def connected():
    user_id = get_jwt_identity()
    ...
```

Le client doit envoyer l'en-tête `Authorization: Bearer <token>`.

### Décorateur `profile_completed`

`utils/decorators.py` définit `profile_completed`, qui applique `@jwt_required()` puis vérifie avec `profile_is_complete` que le profil est complet. Sinon, il renvoie `403` :

```json
{ "error": "incomplet profile", "message": "need to complete your profile." }
```

<Note>
  Ce décorateur n'est encore appliqué à aucune route (il est commenté sur `POST /api/interaction/`). La plupart des routes actuelles ne sont pas protégées par JWT et reçoivent l'identifiant utilisateur dans la requête.
</Note>

## Côté frontend

- `src/services/api_authenticate.ts` : la fonction `login(email, password)` appelle `POST /api/auth/` et renvoie la réponse JSON.
- `src/stores/user.ts` : le store Pinia `useUserStore` conserve `id`, `email`, `username`, `first_name`, `last_name` et `jwt`. Le token est initialisé depuis `localStorage` (clé `token`) et le store est persisté avec `pinia-plugin-persistedstate`.
- `isAuthenticated` vaut `true` dès qu'un token est présent.
- `logout()` déconnecte le socket Socket.IO, vide le store et supprime `token` de `localStorage`.

Il n'existe ni route de déconnexion côté serveur ni jeton de rafraîchissement.
