Matcha utilise **Flask-SocketIO** côté backend et **socket.io-client** côté frontend pour fournir des fonctionnalités temps réel. Cette page décrit la configuration du serveur, l'authentification des connexions, les événements émis et la gestion des rooms, ainsi que les fonctionnalités qui ne sont pas encore implémentées.

## Architecture générale

L'application suit une architecture hybride : les opérations de lecture et d'écriture passent par l'API REST (HTTP + JWT Bearer), tandis que Socket.IO sert à notifier les clients en temps réel. La base de données reste la source de vérité ; Socket.IO ne la remplace pas.

```text
Vue.js
  ├── HTTP + Bearer JWT ───────────────> Flask REST API
  │                                       ├── Vérification JWT
  │                                       ├── Vérification des droits
  │                                       └── Base de données
  │
  └── Socket.IO + JWT à la connexion ──> Flask-SocketIO
                                          └── Événements vers user:<id>
```

<Note>
  Le blueprint de messagerie (`messages_bp`) est commenté dans `app.py` et n'est pas encore activé. Seule l'infrastructure de connexion et de notification est en place.
</Note>

## Configuration serveur

### Initialisation dans `app.py`

Le serveur Flask crée une instance `SocketIO` avec les paramètres suivants :

```python
import os
from flask import Flask
from flask_cors import CORS
from flask_socketio import SocketIO

FRONTEND_ORIGIN = os.getenv(
    "FRONTEND_ORIGIN",
    "http://localhost:5174",
)

app = Flask(__name__)
CORS(app, origins=["http://localhost:5174"])

socketio = SocketIO(
    app,
    cors_allowed_origins=[FRONTEND_ORIGIN],
    async_mode="threading",
    logger=True,
    engineio_logger=False,
)
```

<ParamField body="cors_allowed_origins" type="list">
  Liste des origines autorisées. Par défaut : `http://localhost:5174`.
</ParamField>

<ParamField body="async_mode" type="string">
  Mode asynchrone. Valeur fixée à `threading`.
</ParamField>

<ParamField body="logger" type="boolean">
  Active la journalisation Socket.IO côté serveur (`True`).
</ParamField>

<ParamField body="engineio_logger" type="boolean">
  Journalisation Engine.IO désactivée (`False`).
</ParamField>

### Démarrage du serveur

Le serveur de développement est lancé avec `socketio.run()`, et non `app.run()` :

```python
if __name__ == "__main__":
    socketio.run(
        app,
        host="0.0.0.0",
        port=5000,
        debug=True,
        allow_unsafe_werkzeug=True,
        use_reloader=False,
        log_output=True,
    )
```

<Warning>
  L'utilisation de `socketio.run()` est obligatoire pour que les événements Socket.IO fonctionnent correctement.
</Warning>

## Authentification des connexions

### Principe

Contrairement aux requêtes HTTP qui transmettent le JWT dans l'en-tête `Authorization: Bearer <token>`, Socket.IO envoie le token dans l'objet `auth` lors de la connexion :

```javascript
io("http://localhost:5000", {
  auth: { token: jwtToken }
});
```

Le serveur valide le token côté serveur en vérifiant sa signature et son expiration. L'identité de l'utilisateur est extraite du claim `sub` du payload JWT, jamais depuis un champ libre envoyé par le client.

### Handler `connect` (`sockets/events.py`)

```python
from flask import request
from flask_socketio import join_room
from flask_jwt_extended import decode_token

def register_socket_events(socketio):
    @socketio.on("connect")
    def handle_connect(auth=None):
        if not isinstance(auth, dict):
            return False

        token = auth.get("token")

        if not isinstance(token, str) or not token:
            print("[SOCKET] connexion error: missing token")
            return False

        try:
            payload = decode_token(token)
            user_id = payload.get("sub")

            if user_id is None:
                print("[SOCKET] connexion error: missing user")
                return False

            user_id = str(user_id)
            join_room(f"user:{user_id}")

            print(f"WebSocket connected: user {user_id}")
            return True

        except Exception as exc:
            print(f"[SOCKET] connexion error: unvalid token  {type(exc).__name__}")
            return False
```

<Steps>
  <Step title="Vérification du auth">
    Le paramètre `auth` doit être un dictionnaire. Sinon, la connexion est refusée.
  </Step>
  <Step title="Extraction du token">
    Le token est récupéré via `auth.get("token")`. S'il est absent ou vide, la connexion est refusée.
  </Step>
  <Step title="Décodage JWT">
    La fonction `decode_token` de Flask-JWT-Extended décode le token et extrait le claim `sub`.
  </Step>
  <Step title="Join room">
    L'utilisateur rejoint sa room privée `user:{user_id}`.
  </Step>
</Steps>

### Handler `disconnect` (`sockets/events.py`)

```python
    @socketio.on("disconnect")
    def handle_disconnect(reason=None):
        print(f"WebSocket disconnect : {request.sid}, raison={reason}")
```

Les rooms sont quittées automatiquement par Socket.IO à la déconnexion. Aucune action explicite n'est requise.

## Rooms et ciblage

### Room privée par utilisateur

Chaque utilisateur authentifié rejoint automatiquement une room nommée `user:{user_id}` :

```python
join_room(f"user:{user_id}")
```

Cette room permet d'envoyer des événements spécifiques à un utilisateur, même s'il est connecté depuis plusieurs onglets ou appareils.

### Émission ciblée (exemple théorique)

```python
socketio.emit(
    "new_notification",
    notification_data,
    to=f"user:{recipient_id}",
)
```

<Warning>
  Le serveur ne doit jamais laisser le client rejoindre arbitrairement une room privée. L'identifiant utilisateur est toujours déduit du JWT validé côté serveur.
</Warning>

## Client frontend

### Service `socket.ts`

Le frontend expose une instance Socket.IO partagée dans `front-matcha/src/services/socket.ts` :

```typescript
import { io } from "socket.io-client";

const SOCKET_URL =
  import.meta.env.VITE_SOCKET_URL ?? "http://localhost:5000";

export const socket = io(SOCKET_URL, {
  autoConnect: false,
  transports: ["polling"],
  upgrade: false,
  reconnection: true,
  reconnectionAttempts: 10,
  reconnectionDelay: 1000,
  timeout: 10000,
  auth: (callback) => {
    callback({ token: localStorage.getItem("token") });
  },
});

socket.on("connect", () => {
  console.log("[SOCKET] Connecté :", socket.id);
  console.log("[SOCKET] Transport :", socket.io.engine.transport.name);
});

socket.on("connect_error", (error) => {
  console.error("[SOCKET] Erreur :", error.message);
});
```

<ParamField body="autoConnect" type="boolean">
  Connexion différée (`false`). Le composant appelant doit invoquer `socket.connect()`.
</ParamField>

<ParamField body="transports" type="array">
  Transport forcé à `polling`. L'upgrade vers WebSocket est désactivé (`upgrade: false`).
</ParamField>

<ParamField body="reconnection" type="boolean">
  Reconnexion automatique activée avec 10 tentatives et un délai de 1 seconde.
</ParamField>

<ParamField body="auth" type="function">
  Le token est lu depuis `localStorage` et transmis dans l'objet `auth` au moment du handshake.
</ParamField>

### Composant `SocketTest.vue`

Le composant `SocketTest.vue` montre un exemple d'utilisation du client Socket.IO dans Vue :

```vue
<script setup lang="ts">
import { ref, onMounted, onUnmounted } from "vue";
import { socket } from "../services/socket";

const status = ref("Disconect");
const error = ref("");

function onConnect() {
  status.value = "Connected";
  error.value = "";
}

function onDisconnect() {
  status.value = "Disconect";
}

function onConnectError(err: Error) {
  status.value = "Connexion error";
  error.value = err.message;
}

onMounted(() => {
  socket.on("connect", onConnect);
  socket.on("disconnect", onDisconnect);
  socket.on("connect_error", onConnectError);
  socket.connect();
});

onUnmounted(() => {
  socket.off("connect", onConnect);
  socket.off("disconnect", onDisconnect);
  socket.off("connect_error", onConnectError);
  socket.disconnect();
});
</script>

<template>
  <section>
    <h2>Test WebSocket Matcha</h2>
    <p>État : {{ status }}</p>
    <p v-if="error">Erreur : {{ error }}</p>
  </section>
</template>
```

<Note>
  Le composant s'abonne aux événements `connect`, `disconnect` et `connect_error`, puis invoque `socket.connect()` au montage. Les listeners sont retirés et la connexion fermée au démontage.
</Note>

## Événements émis et reçus

### Événements serveur (handlers actifs)

| Événement | Direction | Description |
| --- | --- | --- |
| `connect` | Client → Serveur | Déclenché à la connexion. Le serveur valide le JWT et joint la room privée. |
| `disconnect` | Client → Serveur | Déclenché à la déconnexion. Les rooms sont quittées automatiquement. |

### Événements non encore implémentés

L'application ne définit actuellement aucun événement personnalisé côté serveur pour diffuser des notifications ou des messages. Le blueprint de messagerie est commenté dans `app.py` :


Les événements suivants sont prévus par l'architecture mais **ne sont pas encore actifs** :

| Événement | Direction | Usage prévu |
| --- | --- | --- |
| `new_message` | Serveur → Client | Notifier un utilisateur qu'il a reçu un nouveau message. |
| `new_notification` | Serveur → Client | Notifier un utilisateur d'une nouvelle alerte (match, like, visite). |
| `notification_read` | Serveur → Client | Confirmer qu'une notification a été marquée comme lue. |

## Ce qui n'est pas encore implémenté

### Chat et messagerie

Le blueprint `messages_bp` est commenté dans `app.py`. Par conséquent :

- Aucune route API n'existe pour créer ou lister des conversations.
- Aucune route API n'existe pour envoyer ou charger des messages.
- Aucun événement Socket.IO `new_message` n'est émis par le serveur.

### Notifications temps réel

Bien que le composant `notification.vue` existe côté frontend pour afficher des toasts de type `success`, `error`, `warning` et `info`, ces notifications sont actuellement déclenchées uniquement par les réponses HTTP de l'API. Il n'y a pas encore de diffusion Socket.IO pour les notifications.

### Diffusion côté serveur

Aucun appel à `socketio.emit()` n'est présent dans les blueprints actuels. Les événements suivants restent à implémenter dans les services concernés :

- Émettre `new_notification` après un like, un match ou une visite de profil.
- Émettre `new_message` après l'enregistrement d'un message en base.

## Sécurité

<Warning>
  Les points suivants sont déjà respectés par l'implémentation actuelle et doivent être maintenus lors de l'ajout de nouvelles fonctionnalités.
</Warning>

- **Authentification** : le JWT est validé côté serveur à chaque connexion via `decode_token`.
- **Room isolation** : chaque utilisateur rejoint uniquement sa room `user:{user_id}`. Le serveur contrôle l'appartenance aux rooms.
- **CORS** : seule l'origine `http://localhost:5174` est autorisée.
- **Pas de trust client** : l'identifiant utilisateur est toujours extrait du token, jamais depuis un paramètre client.

## Diagnostic rapide

| Symptôme | Causes possibles |
| --- | --- |
| `connect_error` | URL ou port incorrect, serveur non démarré, origine refusée, token invalide ou expiré. |
| Connexion établie mais aucun événement | Nom d'événement différent entre client et serveur, aucun `emit()` côté serveur. |
| Événements dupliqués | Plusieurs connexions ou listeners enregistrés plusieurs fois. |
